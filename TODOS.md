## Repos par défaut selon le focus du programme (2026-07-22)

- Retour du user : le repos de base ne devrait pas être une valeur unique (90s) mais dépendre du focus du programme (force / hypertrophie / endurance). Remplacé la constante `DEFAULT_REST_SECONDS = 90` par `DEFAULT_REST_SECONDS_BY_FOCUS: Record<ProgramFocus, number>` dans `sessions-api.ts` :
  - **Force (180s / 3min)** : charges quasi-maximales, récupération ATP-PCr plus complète nécessaire. Repères NSCA (Essentials of Strength Training and Conditioning) et de Salles et al. (2009, Sports Medicine, "Rest Interval between Sets in Strength Training") : ~3-5 min pour le travail force/puissance.
  - **Hypertrophie (90s)** : Schoenfeld, Pope et al. (2016, J Strength Cond Res, "Longer Interset Rest Periods Enhance Muscle Strength and Hypertrophy in Resistance-Trained Men") montrent qu'un repos de 3 min donne des gains de force ET d'hypertrophie égaux ou supérieurs à 1 min, probablement via un meilleur maintien de la charge/du volume sur les séries suivantes — l'ancien réflexe "60s pour la congestion" n'est plus bien soutenu par la littérature récente. 90s reste un compromis raisonnable pour des séries de travail courantes (un repos plus long serait défendable mais moins nécessaire qu'en force pure).
  - **Endurance (45s)** : repères classiques NSCA pour l'endurance musculaire (repos courts, largement sous la minute) pour maintenir le stress métabolique.
  - Ces valeurs restent des **points de départ éditables** — `target_rest_seconds` sur chaque exercice prime toujours sur le défaut du focus.
- Le focus doit maintenant descendre jusqu'à trois endroits : `ProgramDetailPage` (a déjà `program.focus`) → `SessionTemplateCard` (nouvelle prop `focus`) → `ExerciseSlotFormDialog` (nouvelle prop `focus`, utilisée pour le placeholder et le texte d'aide) ; côté log, `SessionLogPage` le lisait via `useProgram(log.program_id)` — depuis le passage offline-first (P3c), il vient du plan mis en cache (`plan.focus`), avec le même repli sur `'hypertrophie'` si le plan n'est pas encore disponible.
- Bug corrigé au passage : `duplicateProgram()` (`programs-api.ts`) copiait les slots d'exercice sans `target_rest_seconds` ni `superset_group` — la liste de champs de l'insert n'avait pas été mise à jour lors de l'ajout de ces deux colonnes dans les phases précédentes. Un programme dupliqué perdait silencieusement ces deux valeurs. Corrigé ; pas de test de duplication existant pour attraper ce genre de régression (`e2e/programs.spec.ts` ne teste que la création) — à surveiller si on ajoute d'autres champs aux exercices planifiés.

## Retour post-gate P3c : retry périodique (2026-07-22)

- Retour du user : pas pu tester sur téléphone (app en localhost, pas accessible depuis le mobile pour l'instant) — test physique reporté à une passe de fin. Point produit important : l'app sera utilisée à ~99% du temps avec la 4G active, pas en vrai mode avion — le cas réaliste du quotidien est plutôt "signal faible/qui coupe par intermittence" que "zéro réseau prolongé".
- Ça a révélé un vrai trou dans la stratégie de retry : `navigator.onLine` reflète seulement si la radio est allumée, pas si les requêtes aboutissent réellement — en 4G faible il peut rester `true` alors que tout timeout. Mon code gérait déjà correctement l'échec ponctuel (toute erreur laisse la ligne `dirty` pour un retry ultérieur), mais les seuls déclencheurs de retry étaient "juste après une écriture" et l'évènement `online` — une coupure de quelques secondes sans nouvelle saisie après pouvait laisser une ligne non synchronisée en attente indéfiniment.
- Ajouté un retry périodique (`setInterval`, 20s) dans `offline-sync.ts`, au niveau du module (tourne tant que l'onglet est chargé, peu importe la page affichée) plutôt que scopé à `SessionLogPage` — plus robuste si l'utilisateur navigue ailleurs pendant qu'une sync est en attente. `syncPendingChanges()` est déjà un no-op bon marché s'il n'y a rien à synchroniser, donc pas de coût réel à cette fréquence.
- Pas de test automatisé dédié à ce timer (mécanique triviale, la logique de sync elle-même est déjà couverte par les 9 tests unitaires existants) — mais à garder à l'esprit si le comportement de retry doit un jour être ajusté (fréquence, backoff, etc.) une fois testé en conditions réelles de 4G.

## P4a — BYOK : gestion des clés API (2026-07-21)

Démarre la "couche IA" du brief (section 4). Contrainte produit explicite du user : chaque utilisateur fournit sa propre clé API (pas de clé partagée côté app) sur Anthropic et/ou OpenAI. Architecture décidée avec le user avant implémentation : clé chiffrée côté serveur (pas 100% client) + relai par Edge Function, les deux providers dès le départ, `Suggestion de deload/recommandation` comme première feature IA prévue pour P4b.

- **Stockage** : `supabase_vault` (pgsodium), déjà activé sur le projet hébergé (`create extension if not exists` a juste confirmé l'existant — pas eu besoin de l'activer manuellement). Nouvelle table `ai_provider_keys` (`user_id`, `provider` check `in ('anthropic','openai')`, `vault_secret_id` → `vault.secrets(id)` `on delete cascade`, `is_valid`, `last_validated_at`) — la ligne ne contient jamais la clé, seulement une référence opaque vers Vault. RLS : policy `select` uniquement pour `authenticated` (`auth.uid() = user_id`) ; volontairement **aucune** policy insert/update/delete — ces écritures passent exclusivement par les Edge Functions via `service_role`, qui gèrent le secret Vault et la ligne de façon atomique.
- **Wrappers Vault** (`public.ai_vault_create_secret/update_secret/read_secret/delete_secret`, `security definer`, `search_path = ''`) : nécessaires car le schéma `vault` n'est pas exposé par PostgREST (seul `public` l'est) — les Edge Functions appellent ces wrappers en RPC via `supabase-js` plutôt que d'ouvrir une connexion Postgres directe. `revoke all ... from public, anon, authenticated` + `grant execute ... to service_role` : vérifié après coup via `information_schema.routine_privileges` que seuls `postgres`/`service_role` ont l'EXECUTE — un `authenticated` ne peut ni lire ni écrire une clé même en appelant les wrappers directement. Les 4 wrappers testés individuellement en direct (`supabase db query --linked`, create → read → update → read → delete → confirmation que la ligne `vault.secrets` a bien disparu) avant d'écrire les Edge Functions par-dessus.
- **Trois Edge Functions** (premières du projet — `supabase/functions/` n'existait pas avant P4a) : `ai-key-save` (valide la clé auprès du provider avant de la stocker, upsert si une clé existait déjà pour ce provider), `ai-key-test` (revalide une clé déjà stockée sans que le user ait à la ressaisir — déchiffre côté serveur via le wrapper, jamais renvoyé au client), `ai-key-delete` (supprime le secret Vault ; la ligne `ai_provider_keys` disparaît par cascade FK, pas de delete explicite sur la table). Toutes vérifient le JWT de l'appelant via un client anon-key avant de créer un second client `service_role` pour les écritures — le `user_id` vient systématiquement du JWT vérifié, jamais du corps de la requête.

## P5a — Data ownership : export JSON et suppression de compte (2026-07-22)

Ferme la première moitié de la section "data ownership" du brief (l'import, plus complexe — remapping d'IDs sur un graphe imbriqué programme→séances→séries — reste en P5b, non commencé).

- **Piège trouvé avant même d'écrire le code** (vérifié en lisant toutes les migrations) : `ai_provider_keys.vault_secret_id` référence `vault.secrets(id) on delete cascade`, mais dans le sens "suppression du secret Vault → suppression de la ligne", pas l'inverse. Une suppression de compte qui se contenterait de `auth.admin.deleteUser()` aurait laissé les secrets Vault (clés Anthropic/OpenAI) orphelins indéfiniment — la cascade FK ne les touche pas. La nouvelle Edge Function `account-delete` nettoie donc explicitement Vault en premier (boucle sur les `ai_provider_keys` du user, `ai_vault_delete_secret` par ligne), puis appelle `admin.deleteUser()` qui cascade tout le reste (`profiles`, `programs`, `session_templates`, `session_template_exercises`, `session_logs`, `session_log_sets`, `weight_entries` — confirmé par lecture de **toutes** les migrations avant d'écrire le code : chaque table a `on delete cascade` vers `auth.users`, directement ou transitivement).
- **Export 100% client** (`src/lib/data-export-api.ts`) : pas d'Edge Function nécessaire, RLS scope déjà toutes les lectures à l'utilisateur courant — même pattern que le reste de l'app. Un objet JSON plat, un tableau par table (`weight_entries`, `exercises` custom uniquement, `programs`, `session_templates`, `session_template_exercises`, `session_logs`, `session_log_sets`) plus `profile`, avec `schema_version`/`exported_at`. `user_id` retiré de chaque ligne (implicite — c'est déjà "les données de cet utilisateur"), `id` conservé pour permettre un remapping de relations lors d'un futur import (P5b). `ai_provider_keys` volontairement absent de l'export — rien d'exportable (juste une référence Vault opaque), et pas une "donnée utilisateur" au sens où on l'entend ici.
- Les types exportés sont dérivés de `Database['public']['Tables'][T]['Row']` via `Omit`/`Pick` plutôt que redéfinis à la main — reste synchronisé automatiquement si une colonne est ajoutée plus tard, cohérent avec l'intention "exporter vraiment tout".
