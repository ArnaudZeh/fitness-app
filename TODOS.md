## Repos par défaut selon le focus du programme (2026-07-22)

- Retour du user : le repos de base ne devrait pas être une valeur unique (90s) mais dépendre du focus du programme (force / hypertrophie / endurance). Remplacé la constante `DEFAULT_REST_SECONDS = 90` par `DEFAULT_REST_SECONDS_BY_FOCUS: Record<ProgramFocus, number>` dans `sessions-api.ts` :
  - **Force (180s / 3min)** : charges quasi-maximales, récupération ATP-PCr plus complète nécessaire. Repères NSCA (Essentials of Strength Training and Conditioning) et de Salles et al. (2009, Sports Medicine, "Rest Interval between Sets in Strength Training") : ~3-5 min pour le travail force/puissance.
  - **Hypertrophie (90s)** : Schoenfeld, Pope et al. (2016, J Strength Cond Res, "Longer Interset Rest Periods Enhance Muscle Strength and Hypertrophy in Resistance-Trained Men") montrent qu'un repos de 3 min donne des gains de force ET d'hypertrophie égaux ou supérieurs à 1 min, probablement via un meilleur maintien de la charge/du volume sur les séries suivantes — l'ancien réflexe "60s pour la congestion" n'est plus bien soutenu par la littérature récente. 90s reste un compromis raisonnable pour des séries de travail courantes (un repos plus long serait défendable mais moins nécessaire qu'en force pure).
  - **Endurance (45s)** : repères classiques NSCA pour l'endurance musculaire (repos courts, largement sous la minute) pour maintenir le stress métabolique.
  - Ces valeurs restent des **points de départ éditables** — `target_rest_seconds` sur chaque exercice prime toujours sur le défaut du focus.
- Le focus doit maintenant descendre jusqu'à trois endroits : `ProgramDetailPage` (a déjà `program.focus`) → `SessionTemplateCard` (nouvelle prop `focus`) → `ExerciseSlotFormDialog` (nouvelle prop `focus`, utilisée pour le placeholder et le texte d'aide) ; côté log, `SessionLogPage` le lisait via `useProgram(log.program_id)` — depuis le passage offline-first (P3c), il vient du plan mis en cache (`plan.focus`), avec le même repli sur `'hypertrophie'` si le plan n'est pas encore disponible.

Un programme dupliqué perdait silencieusement ces deux valeurs. Corrigé ; pas de test de duplication existant pour attraper ce genre de régression (`e2e/programs.spec.ts` ne teste que la création) — à surveiller si on ajoute d'autres champs aux exercices planifiés.

## Retour post-gate P3c : retry périodique (2026-07-22)

- Retour du user : pas pu tester sur téléphone (app en localhost, pas accessible depuis le mobile pour l'instant) — test physique reporté à une passe de fin. Point produit important : l'app sera utilisée à ~99% du temps avec la 4G active, pas en vrai mode avion — le cas réaliste du quotidien est plutôt "signal faible/qui coupe par intermittence" que "zéro réseau prolongé".
- Ça a révélé un vrai trou dans la stratégie de retry : `navigator.onLine` reflète seulement si la radio est allumée, pas si les requêtes aboutissent réellement — en 4G faible il peut rester `true` alors que tout timeout. Mon code gérait déjà correctement l'échec ponctuel (toute erreur laisse la ligne `dirty` pour un retry ultérieur), mais les seuls déclencheurs de retry étaient "juste après une écriture" et l'évènement `online` — une coupure de quelques secondes sans nouvelle saisie après pouvait laisser une ligne non synchronisée en attente indéfiniment.
- Ajouté un retry périodique (`setInterval`, 20s) dans `offline-sync.ts`, au niveau du module (tourne tant que l'onglet est chargé, peu importe la page affichée) plutôt que scopé à `SessionLogPage` — plus robuste si l'utilisateur navigue ailleurs pendant qu'une sync est en attente. `syncPendingChanges()` est déjà un no-op bon marché s'il n'y a rien à synchroniser, donc pas de coût réel à cette fréquence.
- Pas de test automatisé dédié à ce timer (mécanique triviale, la logique de sync elle-même est déjà couverte par les 9 tests unitaires existants) — mais à garder à l'esprit si le comportement de retry doit un jour être ajusté (fréquence, backoff, etc.) une fois testé en conditions réelles de 4G.

## P4a — BYOK : gestion des clés API (2026-07-21)

- **Trois Edge Functions** (premières du projet — `supabase/functions/` n'existait pas avant P4a) : `ai-key-save` (valide la clé auprès du provider avant de la stocker, upsert si une clé existait déjà pour ce provider), `ai-key-test` (revalide une clé déjà stockée sans que le user ait à la ressaisir — déchiffre côté serveur via le wrapper, jamais renvoyé au client), `ai-key-delete` (supprime le secret Vault ; la ligne `ai_provider_keys` disparaît par cascade FK, pas de delete explicite sur la table). ## P5b — Import JSON (2026-07-22)

Ferme la section "data ownership" du brief. Import ajouté dans `src/lib/data-export-api.ts` (`parseUserDataExport` + `importUserData`), même fichier que l'export, réutilise le type `UserDataExport`.

- **`session_templates` n'a pas de policy INSERT — piège trouvé en écrivant le premier jet, corrigé avant même de tester** : chaque programme reçoit ses 7 jours fixes (lundi-dimanche) via un trigger `on_program_created` à la création (`20260721220320_fixed_weekdays_session_templates.sql`), et la policy insert a été explicitement supprimée à l'époque pour préserver l'invariant "toujours exactement 7 jours". Importer un jour ne peut donc jamais être un insert — le code récupère les 7 jours déjà auto-créés sur le nouveau programme (matchés par `day_of_week`, la vraie clé naturelle de la table) et fait un `update` de leur `day_type` plutôt qu'un insert. Repéré en lisant la policy RLS live (`pg_policies`) avant d'écrire le code, pas après un échec — mais la suite a quand même révélé deux bugs réels, tous deux trouvés en testant le scénario "exporter puis réimporter dans le même compte" via e2e (`e2e/data-import.spec.ts`), un cas que rien d'autre dans le repo n'exerçait jusqu'ici :
  1. **Collision de tri sur `created_at`** : la première version préservait `created_at`/`updated_at` de l'export sur les lignes recréées (programmes, exercices, `session_template_exercises`, `session_logs`, `session_log_sets`) — cohérent en apparence avec la philosophie "restaurer les vraies données", mais un programme réimporté dans le même compte se retrouvait avec le **même `created_at`, à la microseconde près**, que l'original. Comme `fetchPrograms()` trie par `order by created_at desc` sans tie-breaker, Postgres ne garantit aucun ordre stable entre deux lignes à égalité — la liste changeait d'ordre de façon non déterministe entre deux refetch, un vrai bug produit (pas juste un souci de test) pour quiconque réimporte dans un compte non-vide. Corrigé : seules les dates réellement porteuses de sens métier restent préservées (`recorded_at` des pesées, `started_at`/`completed_at` des séances loguées — celles dont dépendent les graphes Analytics) ; `created_at`/`updated_at`, simples métadonnées de ligne sans lecteur applicatif, ne sont plus reportés — chaque ligne importée reçoit un timestamp frais.
  2. **`invalidateQueries()` sans filtre dans `useImportUserData`, combiné à un bug préexistant dans `usePrograms.ts`** : `useDeleteProgram`/`useCreateProgram`/`useDuplicateProgram` avaient `onSuccess: () => queryClient.invalidateQueries(...)` (corps d'expression, donc la promesse est **retournée**, pas juste déclenchée) — `mutateAsync()` attend cette promesse avant de se résoudre. Supprimer un programme depuis sa page de détail invalide `['programs']`, qui matche en préfixe la query `['programs', id]` **encore montée** (on est toujours sur cette page) ; son refetch échoue (la ligne vient de disparaître) et retry avec backoff avant que l'invalidation ne se résolve — le bouton de suppression restait désactivé plusieurs secondes, parfois au-delà du timeout de test. `useUpdateProgram` avait déjà le bon pattern (`void queryClient.invalidateQueries(...)`, non bloquant) ; aligné `useCreateProgram`/`useDeleteProgram`/`useDuplicateProgram` dessus. Bug préexistant, pas introduit par l'import — mais l'invalidation globale (`invalidateQueries()` sans clé) de la première version de `useImportUserData` ajoutait une charge de fond qui le rendait beaucoup plus visible ; corrigé aussi en scopant l'invalidation de l'import aux 5 clés réellement concernées (`profile`, `weight-entries`, `programs`, `exercises`, `set-history`) plutôt qu'une invalidation globale.
  - **Backlog** : le même pattern bloquant (`onSuccess` sans `void`) existe dans `useAiProviderKeys.ts`, `useExercises.ts`, `useSessionTemplates.ts`, `useWeightEntries.ts` — pas corrigé ici faute de preuve concrète d'impact (aucun test ne l'a fait apparaître), mais candidat à un passage de nettoyage dédié.

## P6b — Notifications push PWA pour le planning bien-être (2026-07-22)

Deuxième moitié de la section "Planning bien-être quotidien" du brief. `reminder_time` existait déjà dans le schéma depuis P6a (colonne inexploitée) ; P6b ajoute toute l'infrastructure pour réellement envoyer un rappel au moment prévu.

- **Service worker custom** : bascule de `generateSW` (stratégie par défaut de `vite-plugin-pwa`, utilisée jusque-là) à `injectManifest` — `generateSW` génère un SW opaque sans place pour du code custom, alors qu'un rappel push a besoin d'écouter `push` et `notificationclick` soi-même. `src/sw.ts` : précache via `workbox-precaching` (`precacheAndRoute(self.__WB_MANIFEST)`, seule brique conservée de `generateSW`), `push` affiche une notification à partir du payload JSON (titre/corps/URL, avec un fallback générique si le payload est absent ou malformé), `notificationclick` referme la notification et navigue/focus un client existant vers l'URL (`/bien-etre` par défaut) ou ouvre une nouvelle fenêtre sinon.
- **Paire de clés VAPID** générée une fois (`web-push generate-vapid-keys`) : la publique va dans `VITE_VAPID_PUBLIC_KEY` (`.env.local`, safe à exposer côté client — c'est le principe même de la paire publique/privée), la privée uniquement comme secret d'Edge Function (`supabase secrets set VAPID_PRIVATE_KEY=...`), jamais commitée nulle part.
- **`profiles.timezone`** (IANA, ex. `Europe/Paris`) : `reminder_time` est une heure murale saisie dans le navigateur, mais le scheduler tourne côté serveur en UTC — sans fuseau stocké, un rappel à 7h partirait à 7h UTC. Auto-détecté côté client (`Intl.DateTimeFormat().resolvedOptions().timeZone`) et synchronisé silencieusement à chaque chargement de l'app (`syncTimezone()` dans `profile-api.ts`, appelé depuis un `useEffect` de `AppLayout` — donc sur toute route authentifiée, pas seulement `/bien-etre`) ; best-effort, une erreur réseau est avalée (`.catch(() => {})`) plutôt que de casser l'affichage pour une donnée non bloquante. Comparaison avant écriture pour éviter un `update` inutile à chaque visite quand le fuseau n'a pas changé.
- **`push_subscriptions`** (nouvelle table, P6a→P6b) : un abonnement par `endpoint` (déjà unique par device/navigateur de par la Push API elle-même), RLS standard scopée `auth.uid() = user_id`. **Piège trouvé après coup, corrigé dans une migration séparée** : la migration initiale n'avait que select/insert/delete, pas de policy update — or le client fait un `upsert(..., { onConflict: 'endpoint' })` pour gérer le cas "même navigateur se réabonne" (ex. après avoir désactivé puis réactivé), et le chemin `ON CONFLICT DO UPDATE` nécessite une policy UPDATE même si l'intention initiale était "jamais de update direct". Migration `20260722160000` ajoutée plutôt que d'éditer la migration déjà poussée en base.
- **`wellness_reminder_sends`** : registre d'envoi interne au scheduler, RLS activée sans **aucune** policy pour `authenticated` (même raisonnement que l'absence de policy insert sur `session_templates`) — `unique(activity_id, sent_date)` sert de verrou d'idempotence : si deux exécutions du cron se chevauchent, la seconde reçoit une violation de contrainte sur l'insert et saute l'envoi plutôt que de notifier deux fois.
- **Edge Function `send-wellness-reminders`** : pour chaque activité active avec un `reminder_time`, convertit l'heure serveur (UTC) en heure murale du fuseau du propriétaire (`Intl.DateTimeFormat` avec `timeZone` + `hourCycle: 'h23'`), compare au `reminder_time`/jour de la semaine de l'activité, insère dans `wellness_reminder_sends` (verrou d'idempotence ci-dessus) puis envoie via `npm:web-push` à tous les abonnements du user. Un abonnement qui répond 404/410 (device désinstallé, permission révoquée, données navigateur effacées) est auto-supprimé de `push_subscriptions` plutôt que retenté indéfiniment.
- **Auth de la fonction — deux essais, le premier a échoué en test réel, pas juste en théorie** : cette fonction n'est appelée que par `pg_cron`/`pg_net`, jamais par un utilisateur final — pas de JWT de session à vérifier. Premier essai : comparer l'en-tête `Authorization` à `Bearer ${SUPABASE_SERVICE_ROLE_KEY}` (le secret auto-injecté par la plateforme dans chaque Edge Function). Testé en direct avec la vraie clé `service_role` récupérée via `supabase projects api-keys` : rejeté (401) — la valeur auto-injectée dans le runtime des fonctions ne correspond pas à celle renvoyée par cette commande CLI (probablement un format de clé différent/rotation). Abandonné au profit d'un secret dédié et généré par nous (`CRON_SECRET`, 32 octets aléatoires), stocké à la fois comme secret d'Edge Function et dans Supabase Vault (`vault.create_secret(..., 'cron-invoke-secret')`), envoyé via un en-tête custom `x-cron-secret` plutôt que `Authorization` — celui-ci est de toute façon intercepté par la vérification JWT de la plateforme *avant* que le code de la fonction ne s'exécute (confirmé en observant `UNAUTHORIZED_NO_AUTH_HEADER`, une erreur qui ne vient pas de notre code). Fonction déployée avec `--no-verify-jwt` (`[functions.send-wellness-reminders] verify_jwt = false` dans `config.toml`, pour que les futurs redéploiements gardent ce comportement) puisqu'il n'y a structurellement aucun JWT à vérifier ici.
- **`pg_cron` + `pg_net`** (migration `20260722150000`, jamais activés sur ce projet avant P6b) : job `send-wellness-reminders-every-minute` (`* * * * *`) qui appelle `public.invoke_send_wellness_reminders()`, une fonction `security definer` qui lit `cron-invoke-secret` depuis `vault.decrypted_secrets` puis fait `net.http_post` vers l'Edge Function avec l'en-tête `x-cron-secret` — le secret n'apparaît jamais en clair dans une migration committée, seulement au moment de l'exécution côté serveur.
- **Vérifié en direct, pas juste par lecture du code** : `curl` sans en-tête → 401 (plateforme) ; avec `x-cron-secret` invalide → 401 (notre check) ; avec la vraie valeur → `200 {"sent":0,"skipped":0}` (aucun abonnement/activité en base au moment du test, réponse attendue). Après le `db push` de la migration cron, confirmé `cron.job` contient bien le job actif puis attendu ~75s en tâche de fond (`Monitor`) pour voir une ligne apparaître dans `cron.job_run_details` avec `status = 'succeeded'` — le job tourne réellement en prod, pas seulement "créé sans jamais s'exécuter".
- **Client — abonnement push** (`src/lib/push-api.ts`, `src/hooks/useNotifications.ts`) : `getNotificationSupport()` distingue trois états — `supported` (Notification/serviceWorker/PushManager présents), `ios-not-installed` (Safari iOS n'expose la Web Push API qu'à une PWA ajoutée à l'écran d'accueil ; sans ça `Notification`/`PushManager` sont simplement absents du `window`, indiscernable de "pas supporté du tout" sans détecter spécifiquement ce cas via `navigator.userAgent` + `matchMedia('(display-mode: standalone)')`), et `unsupported` (carte masquée entièrement). `subscribeToPush` : demande la permission, `pushManager.subscribe()` avec la clé VAPID publique convertie en `Uint8Array`, puis `upsert` de l'endpoint/clés dans `push_subscriptions`. `unsubscribeFromPush` : supprime la ligne DB puis appelle `subscription.unsubscribe()` (dans cet ordre — si la ligne DB restait après un `unsubscribe()` réussi, le scheduler tenterait d'envoyer à un endpoint mort jusqu'au prochain cycle d'auto-nettoyage 404/410).
- **Détail TypeScript** : `Uint8Array.from(...)` type désormais en `Uint8Array<ArrayBufferLike>`, que `PushSubscriptionOptionsInit.applicationServerKey` (qui attend un `ArrayBufferView<ArrayBuffer>`) rejette — remplacé par `new Uint8Array(length)` rempli par boucle, dont le buffer sous-jacent est garanti `ArrayBuffer` (pas `SharedArrayBuffer`). Erreur qui n'apparaissait qu'en `tsc -b` (mode projet, utilisé par `npm run build`), pas en `tsc --noEmit` seul — piège à surveiller si un futur diagnostic type-check en local ne matche pas ce que `npm run build` rapporte.
- **UI** : nouvelle carte "Notifications" sur `/bien-etre` (au-dessus du formulaire de création), masquée si `unsupported`, message dédié "ajoutez à l'écran d'accueil" si `ios-not-installed`, sinon bouton "Activer/Désactiver les notifications" reflétant l'état d'abonnement réel du navigateur (pas juste un flag local — relit `pushManager.getSubscription()` au montage).
- **Non vérifié cette session, à faire par le user** : la réception réelle d'une notification (créer une activité avec un `reminder_time` proche, s'abonner depuis un vrai navigateur, attendre le rappel, cliquer dessus pour confirmer l'ouverture sur `/bien-etre`) — délibérément non testé via le navigateur automatisé cette session : la vérification manuelle P6a a montré qu'un onglet Chrome peut porter une session déjà authentifiée sur le **vrai compte** plutôt que le compte e2e-fixture, et s'abonner réellement pousserait une vraie ligne `push_subscriptions` + potentiellement un vrai push vers ce compte. Toute l'infrastructure serveur (auth de la fonction, cron, idempotence) a en revanche été vérifiée en direct comme détaillé ci-dessus.
- Tests : `e2e/wellness.spec.ts` étendu d'un test vérifiant que la carte "Notifications" s'affiche avec un bouton "Activer les notifications" actif (Chromium headless expose bien `Notification`/`serviceWorker`/`PushManager`) — le clic réel n'est pas testé (déclencherait un vrai abonnement contre le service de push de Google depuis l'environnement de test, potentiellement flaky et laissant une ligne persistante sur le compte fixture), cohérent avec le même choix déjà fait pour le chemin "clé IA valide" en P4a.

## P7 — Hypoxie intermittente (2026-07-22)

Un arrêt manuel en cours de récupération du cycle N logge donc `completed_cycles = N` ; un arrêt en cours d'apnée du cycle N logge `N - 1`. Rien n'est loggé si l'utilisateur arrête avant même d'avoir terminé une seule apnée (`completed_cycles = 0` volontairement pas inséré — une tentative avortée immédiatement n'est pas une "session").
- **Minuteur plein écran** (`BreathRunner` dans `BreathPage.tsx`) : state machine pure (`RunnerState { phase, cycleIndex, secondsLeft }` + fonction `advance()` déterministe) plutôt qu'un enchaînement de `useState` épars — apnée → récup, répété `cycles` fois, puis `phase: 'done'`. ## P9b — Couche sociale : tonnage hebdo + streak de régularité (2026-07-23)

Deux jalons supplémentaires annoncés dans le scope initial de la couche sociale (P9a), livrés séparément comme prévu pour rester dans la taille de phase habituelle.

- **Bucketing de semaine identique au client** : `public.iso_week_start(timestamptz)` (SQL, `immutable`) reproduit exactement `getIsoWeekStart` (`src/lib/analytics.ts`) — `date_trunc('week', ...)` de Postgres suit déjà la définition ISO 8601 (lundi), il suffisait de normaliser la date en UTC avant troncature pour coïncider avec le calcul client (`.slice(0,10)` sur un timestamp déjà UTC). Un seul point de vérité pour "quelle semaine" plutôt que de dupliquer le calcul dans chaque trigger.
- **`week_start date`** ajouté à `milestones` (nullable — `one_rep_max` n'en a pas besoin), avec deux **index uniques partiels** (`where milestone_type = 'weekly_tonnage'` / `'regularity_streak'`) plutôt qu'une contrainte globale, pour ne jamais limiter `one_rep_max` à une ligne par semaine.
- **Tonnage hebdo — la valeur doit pouvoir grandir, pas se figer** : contrairement à `one_rep_max` (une ligne par record, jamais modifiée), le tonnage de la semaine en cours continue d'augmenter à mesure que d'autres séries sont loguées. Figer la valeur au moment où le seuil est franchi montrerait un total sous-évalué en fin de semaine. Le trigger utilise donc `insert ... on conflict (user_id, week_start) where milestone_type = 'weekly_tonnage' do update set value = excluded.value where milestones.value < excluded.value` — une seule ligne par semaine-record, toujours à jour avec le total le plus élevé réellement atteint. Chaque nouvelle semaine qui bat le record all-time précédent obtient sa **propre** ligne (l'historique s'accumule, comme pour `one_rep_max` — pas un seul "record actuel" qu'on écrase).
- **Streak de régularité — "gaps and islands" classique en SQL** : semaines actives (au moins une série loguée) triées par ordre décroissant, `semaine + (rang × 7 jours)` reste constant sur une série de semaines consécutives — grouper là-dessus isole chaque "île" d'activité sans boucle procédurale. Le streak courant est la longueur du groupe le plus récent ; comparé au meilleur des **autres** groupes (`filter (where recency_rank > 1)`) pour savoir si c'est un nouveau record. **Seuil à 2 semaines minimum** avant qu'un streak soit annoncé — sans ce garde-fou, la toute première semaine d'usage de n'importe quel utilisateur génère un "record : 1 semaine" immédiatement, du bruit pur.
- **Vérifié en direct avec des données antidatées, pas seulement en lisant le SQL** : programme/exercice/séries de test insérés directement via `supabase db query` avec des `started_at` répartis sur 4-6 semaines ISO réelles (2026-06-29 à 2026-08-03), scénario par scénario — semaines consécutives (streak progresse 1→2→3, sous le seuil de 2 non annoncé puis annoncé), tonnage qui grandit au sein d'une même semaine-record (vérifié que la ligne se **met à jour** plutôt que de dupliquer, testé explicitement avec 3 séries successives dans la même semaine), semaine plus légère qui ne bat pas le record (aucune ligne créée), **trou dans le streak** (saut d'une semaine → streak retombe à 1, non annoncé, l'ancien record de 3 reste intact), nouveau streak après le trou qui n'atteint pas l'ancien record (2 < 3, non annoncé). Les tests par simple usage réel de l'app (via le navigateur) ne pouvaient pas exercer ces scénarios multi-semaines sans attendre plusieurs semaines en temps réel — vérification directe en base la seule option praticable, avec le même niveau de rigueur que pour la formule 1RM en P9a.
- **Refactor de passage** : `MILESTONE_TYPE_LABELS`/`formatMilestoneValue` extraits de `social-api.ts` (qui importe `supabase`, donc pas testable unitairement sans mock) vers un nouveau `src/lib/social-display.ts` pur — même séparation déjà établie pour `cycle-phase.ts`/`cycle-api.ts` en P8. `formatMilestoneValue` gère l'affichage par type (kg avec décimales pour `one_rep_max`, kg arrondi pour `weekly_tonnage`, "X semaine(s) d'affilée" avec pluriel correct pour `regularity_streak`) — testé unitairement (`social-display.test.ts`, 4 tests).
- **Test e2e étendu, pas dupliqué** : le test P9a existant (999kg x 5) sert aussi de test tonnage — 4995kg de tonnage en une seule série dépasse largement tout ce que les autres specs de la suite peuvent produire cette semaine-là, donc fiable comme "nouveau record" sans configuration supplémentaire. Pas de test e2e pour le streak (nécessiterait des données antidatées, hors de portée d'un test piloté par navigateur qui logue toujours au temps réel) — couvert par la vérification directe en base ci-dessus.
- **Vérifié en direct côté app** : `tsc --noEmit`, ESLint, build complet, 81 tests unitaires (3 nouveaux). Suite e2e complète (28 tests) rejouée après implémentation, verte. Fixture account nettoyé après chaque run.

## P9c — Couche sociale : photos de progression (2026-07-23)

Dernier morceau du scope initial de la couche sociale. Premier bucket Supabase Storage du projet.

- **Bucket privé, jamais d'URL publique** : `progress-photos` (`public = false`, 5 Mo max, JPEG/PNG/WebP). Convention de chemin `<user_id>/<uuid>.jpg` — le premier segment sert de propriétaire pour les policies RLS Storage (`storage.foldername(name)`). Même règle de visibilité que `milestones`/`public_profiles` (soi-même, ou un utilisateur avec `social_sharing_enabled`), appliquée à la fois sur `storage.objects` (accès au fichier) et sur `progress_photos` (la ligne en base) — les deux doivent être cohérentes puisque ce sont deux systèmes RLS indépendants.
- **Accès en lecture via URL signée**, pas `getPublicUrl()` (qui ne vérifie aucune permission — inutilisable sur un bucket privé) ni téléchargement de blob manuel. `createSignedUrl()` respecte RLS à la génération : demander une URL signée pour un chemin auquel on n'a pas droit échoue, avant même d'atteindre le fichier. Expiration à 1h, régénérée à chaque chargement du feed — largement suffisant pour une consultation, pas besoin de cache.
- **Compression côté client, aucune nouvelle dépendance** : `compressImage()` (`src/lib/image-compression.ts`) utilise `createImageBitmap` + `<canvas>` natifs du navigateur — redimensionne à 1600px de long côté max, réexporte en JPEG qualité 0.82. Une vraie photo de téléphone (3-8 Mo) devient une fraction de ça avant l'upload, pertinent pour un usage mobile-first sur un quota Storage limité (palier gratuit).
- **Bug trouvé en vérifiant avec un vrai compte jetable, pas en lisant le code — lacune réelle dans `account-delete` (P5a)** : `admin.auth.admin.deleteUser()` cascade bien la ligne `progress_photos` (vraie FK vers `auth.users`), mais **pas** le fichier Storage sous-jacent — confirmé par test direct (upload + suppression du compte + le fichier restait dans le bucket). Même famille de piège que `ai_provider_keys`/Vault trouvé en P5a (une ressource référencée depuis une table qui cascade, mais dont la cascade ne suit pas jusqu'à la ressource elle-même). Corrigé : `account-delete` liste et supprime maintenant les objets Storage du user avant `deleteUser()`. Redéployé et re-vérifié avec un nouveau compte jetable : `auth.users`, `progress_photos` et l'objet Storage sont tous à zéro après suppression.

## Couche IA — étape 2 : génération de programme par l'IA (2026-07-23)

Deuxième étape de la feuille de route "coach privé" du user. Cadrage confirmé avant implémentation (AskUserQuestion) : paramètres précisés par l'utilisateur avant génération (jours/semaine, équipement, contraintes — pas de déduction 100% automatique), et l'IA ne peut proposer que des exercices déjà pratiqués par l'utilisateur (pas tout le catalogue système). Toujours "propose puis révise" : l'IA ne crée jamais de programme silencieusement, l'utilisateur voit un aperçu en lecture seule et confirme avant toute écriture réelle.

- **`supabase/functions/_shared/ai-program-generation.ts`** (nouveau) : logique partagée d'appel provider pour la génération structurée, sur le modèle de `ai-analysis.ts`. Un même schéma JSON (`PROGRAM_PROPOSAL_SCHEMA`, avec `additionalProperties: false` et toutes les propriétés listées dans `required` — nécessaire pour le mode strict d'OpenAI, inoffensif pour Anthropic) sert aux deux chemins :
  - **Anthropic** : tool-use forcé (`tool_choice: {type:'tool', name:'propose_program'}`). **`thinking` volontairement omis** pour cet appel précis — la réflexion étendue d'Anthropic est incompatible avec un `tool_choice` forcé (le modèle doit rester libre de décider s'il réfléchit avant de s'engager sur un outil), et un `tool_choice` forcé est ce qui rend la sortie structurée assez fiable pour être appliquée sans relecture humaine ligne par ligne. Contrairement à l'analyse de tendance (texte libre, où `thinking: adaptive` reste actif), ce compromis est spécifique à cet appel.
  - **OpenAI** : `response_format: {type:'json_schema', json_schema:{name, strict:true, schema}}`, même schéma que côté Anthropic.
  - **Validation serveur post-réponse** (`validateProposal`) avant que quoi que ce soit ne quitte l'Edge Function : chaque `exerciseId` renvoyé doit appartenir au pool autorisé fourni par le client, `targetRepsMax >= targetRepsMin`, exactement 7 jours couvrant chacun des 7 jours de la semaine une seule fois. Le schéma garantit la *forme*, pas que le modèle a respecté ses propres instructions — un modèle peut toujours inventer un exercice hors liste malgré la consigne, donc re-vérifié côté serveur plutôt que de faire confiance au prompt seul.
- **`PROGRAM_GENERATION_SYSTEM_PROMPT`** (`coach-persona.ts`) : `COACH_PERSONA` + règles de structure spécifiques (répartition réaliste des jours, `target_reps_max >= target_reps_min`, adaptation séries/reps/RPE au focus choisi et à l'objectif du profil, contraintes utilisateur traitées comme donnée à respecter jamais comme instruction qui outrepasse les garde-fous du persona — notamment jamais de diagnostic médical même si une contrainte évoque une douleur).
- **`supabase/functions/_shared/fetch-with-timeout.ts`** (nouveau) : le helper de timeout de `ai-analysis.ts` extrait tel quel, maintenant partagé entre les deux Edge Functions plutôt que dupliqué.
- **`supabase/functions/ai-generate-program/index.ts`** (nouveau) : même structure auth/clé que `ai-analyze-trends` (401 non authentifié, 400 provider/profil/exercices/jours invalides, 404 aucune clé enregistrée, 502 si le provider échoue). `availableExercises` doit être un tableau non vide, `daysPerWeek` entre 1 et 7.
- **`src/lib/program-generation-api.ts`** (nouveau, côté client) : `generateProgram()` relaie au provider via l'Edge Function. **`applyProgramProposal()` réutilise exactement les fonctions existantes de `programs-api.ts`/`sessions-api.ts`** (`createProgram`, `fetchSessionTemplates`, `updateSessionTemplateDayType`, `createSessionTemplateExercise`) en suivant le pattern de `duplicateProgram()` — jamais de chemin d'écriture bespoke pour la sortie de l'IA. Le repos par défaut vient de `DEFAULT_REST_SECONDS_BY_FOCUS[proposal.focus]`, pas d'un champ décidé par le modèle (cohérent avec P3b : ce n'est pas à l'IA de fixer cette valeur).
- **Exercices "déjà pratiqués"** dérivés côté client de `useSetHistory()` (les séries réellement loguées, `session_log_sets`), pas de la table `exercises` (catalogue global partagé entre tous les utilisateurs, y compris des exercices jamais pratiqués) — cohérent avec le cadrage confirmé.
- **UI** : nouvelle page `/programs/generate` (lien "Générer avec l'IA" depuis `ProgramsListPage`, à côté de "Nouveau programme"). Trois états : aucune clé configurée / aucun exercice logué (mêmes gardes que la carte Analyse IA du Dashboard), formulaire (jours/semaine, équipement, contraintes, sélecteur de provider si plusieurs configurés), aperçu en lecture seule (nom, focus, justification, répartition des 7 jours) avec actions "Créer ce programme" / "Régénérer" / "Annuler".
